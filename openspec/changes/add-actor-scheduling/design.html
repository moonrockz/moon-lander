Context

See proposal.md for the motivation. This change builds on add-typed-actors, which is not yet implemented. That change makes actor logic a Receive value that only the runtime or a test runner runs, and its TEST-1 decision gives every wait to the runtime. Its runtime uses moonbitlang/async 0.22.5 on wasm, js and native. That library gives sleep, now, with_timeout_opt and task groups; it has no scheduler, no virtual time and no way to run ready tasks until they are idle.

Labels identify the source of a decision. Owner means the user requested it. Call means this proposal chooses it for review.

Goals and non-goals

Goals: scheduled and repeated sends that belong to actor lifetimes, follow the admission rules, and can be tested with no real waiting. The basic forms use the shared Erlang, Elixir and Gleam name send_after.

Non-goals: the items under "Out of scope" in the proposal, and any change to the public API of add-typed-actors.

Decisions

SCHED-1. A separate change, implemented after add-typed-actors (Owner, 2026-10-29)

Scheduling is its own change so that add-typed-actors stays reviewable. The owner approved implementation on 2026-10-29 as a follow-up goal after add-typed-actors, in the same workspace. It starts after add-typed-actors groups 4 and 6. A release of both changes follows.

CLK-1. One internal clock boundary (Owner: internal only, 2026-10-29)

The runtime reads time and waits only through one internal clock: the current time and a cancellable wait until a deadline. Receive time limits (within), ask deadlines, cleanup budgets and timers all use it. The real clock wraps @aio.now and @aio.sleep. The clock is internal; scopes and the test runner select it with an optional argument. Today the actor spike calls @aio.with_timeout_opt directly; group 1 replaces those calls with a race against a clock wait.

Alternative: give each operation its own sleep. Rejected because a test clock could then not control all waits, and TEST-1 of add-typed-actors requires that tests need no real time.

Alternative: a public clock interface that applications implement. Rejected by the owner on 2026-10-29: the real clock and TestClock are the only clocks, which keeps the API small.

CLK-2. A deterministic test clock (Owner: explicit advance only, 2026-10-29; Call: API)

TestClock starts at zero and changes only through advance(limit). Advancing fires due waits one at a time, in deadline order, ties in schedule order. After each firing it lets the woken tasks run before it fires the next one, so effects happen in the same order as with real time.

async test "a session expires after thirty seconds" {
  let clock = @actors.TestClock::new()
  @actors.scope(clock~) <| scope => {
    let session = scope.spawn() <| _ => { session_receive() }
    let timer = scope.send_after(session.to_ref(), thirty_seconds, Expire)
    clock.advance(thirty_seconds)
    assert_eq(session.join(), Expired)
    ignore(timer)
  }
}

The receive test runner also takes a script of deliveries and clock advances, so a protocol with time limits is a unit test with no scope:

async test "login times out after five seconds" {
  let result = login() |> @actors.run_script([
    Deliver(Hello("ann")),
    Advance(five_seconds),
  ])
  assert_eq(result, Some("timed out"))
}

The clock never advances on its own, also when every task waits. Alternative: jump to the next deadline when all tasks wait, which makes some tests shorter. Rejected by the owner on 2026-10-29, because a test could then pass through a time jump at a moment that the test did not choose.

The pinned moonbitlang/async has no "run until idle" operation. "Let the woken tasks run" therefore needs a proof: group 1 starts with a spike that shows deterministic ordering on wasm, js and native, or revises this decision before the rest.

SEND-1. Scope-owned scheduled send (Call; Owner: admitted messages stay, 2026-10-29)

scope.send_after(target, delay, message) sends one message to a Subject[M] or ActorRef[M] after a TimeLimit and returns a Timer. Timer::cancel() returns Stopped when the message was not sent, or AlreadyFired when it was admitted; an admitted message stays queued, as the admission rules of add-typed-actors require. The scope cancels its timers before it cancels its actors, and an escaped scope rejects new timers with the typed closed-scope error.

SCHED-2. Pure schedule values (Owner: these forms and the default, 2026-10-29)

Schedule is an opaque, immutable value in the portable root, so it builds and tests on all four targets. It has these constructors and limits:

FormDelays
Schedule::fixed_delay(limit)The same delay each time
Schedule::exponential(first~, maximum~)Doubles from first and stays at maximum
schedule.up_to(count)At most a MessageCount of sends
schedule.delays()The delays as an iterator, for tests and documentation

The growth factor is fixed at two, so no unchecked factor enters the API. Delays use TimeLimit; doubling stops at maximum, so no delay leaves its range. Without up_to, a schedule repeats until it is cancelled, as Erlang, Elixir and Akka timers do. Other forms, such as a linear step or an explicit list of delays, can come later without a breaking change.

Alternative: reuse @aio.RetryMethod. Rejected because it holds raw Int milliseconds and a raw Double factor, and it describes retries, not message sends.

SEND-2. Repeated sends with fixed delay and admission backpressure (Owner: fixed delay only and the name send_repeated, 2026-10-29)

scope.send_repeated(target, schedule, message) returns a Timer. The name matches start_repeated of actor timers. Each delay starts after the previous message is admitted. When the mailbox is full, the send waits, so ticks never pile up and no message is dropped. The repeated send stops at the end of the schedule, on cancel, at scope exit, or when the target closes; a closed target is a normal end, not a scope failure.

Alternatives: fixed rate, which catches up after a delay and can send bursts into a slow actor; and skip or merge a tick when the mailbox is full, which would silently drop a message against the actor admission rules. Both are rejected for this change. Other names considered: send_on, which is unclear, send_on_schedule, which is long, and Erlang's send_interval, which suggests a fixed interval although a schedule can grow.

TIMER-1. Actor-owned keyed timers (Call; Owner: stale messages never received, 2026-10-29)

Through its context, an actor gets a timer table typed by its protocol and by an application key type K : Eq + Hash, usually a small enum. The table belongs to the actor lifetime: all its timers stop when the actor ends.

enum TimerKey {
  Poll
  Expire
} derive(Eq, Hash)

let poller = scope.spawn() <| ctx => {
  let timers : @actors.Timers[Feed, TimerKey] = ctx.timers()
  timers.start_repeated(Poll, @actors.Schedule::fixed_delay(five_seconds), Tick)
  timers.start_single(Expire, one_hour, Shutdown)
  @actors.receive_loop(0) <| (count, message) => { ... }
}

Starting a timer with a key that is already in use cancels the old timer first. A message that a cancelled or replaced keyed timer has already queued never reaches a receive, as in Akka. Stale ticks after a replacement are a common timer bug, and only the runtime can remove them reliably. send_after and send_repeated keep the plain rule: their admitted messages stay queued.

To find stale messages, each mailbox entry gets an internal tag: no tag for ordinary sends, and a timer identity and generation for keyed timer sends. Cancel and replace mark that generation stale. The runtime removes stale entries at once when no select is waiting; otherwise it skips and removes them when a receive reaches them, so the index of a waiting select stays valid. A stale entry counts toward capacity and queued_count until the runtime removes it. This is a cancellation that the application asked for, not a mailbox policy, so the "no silent drop" admission rule of add-typed-actors still holds for every other message. The tag is an internal change to the add-typed-actors mailbox; no public API of that change changes.

Alternatives: keep admitted messages and let the application ignore stale ones, which repeats the same check in every actor; or report the count of queued stale messages from cancel, which still leaves the work to the application. The owner chose removal for keyed timers on 2026-10-29.

Typed keys follow the domain-type rule: no string keys. Group 1 compiles this shape; an explicit type annotation at ctx.timers() may be necessary because the key type does not appear in the arguments.

Risks and trade-offs

RiskMitigation
The pinned async library cannot run ready tasks until idle, so a test clock could fire timers in a different order than real time.A group 1 spike proves deterministic ordering on wasm, js and native before the rest; revise CLK-2 if it cannot.
A timer fires late when a handler does not yield.State the cooperative limit; no hard real-time promise.
A repeated send to a slow actor delays its later ticks.Fixed delay from admission is the documented behavior; applications that need a deadline use within.
Timers that outlive their scope would leak tasks.Scopes own timers and cancel them first at exit; actor timer tables end with the actor; tests check that no timer task remains.
The tagged mailbox entry for keyed timers adds work to every receive and could break the selective-receive index.Remove stale entries at once only when no select waits; otherwise skip them when a receive reaches them. Run the add-typed-actors admission, selective-receive and stack tests unchanged, and compare the local benchmark before and after.
The clock boundary changes internal code of add-typed-actors.No public API changes; that change's acceptance tests run unchanged on the real clock.

Migration plan

Additive. Implement after add-typed-actors groups 4 and 6. No release is part of this change; a separate owner-approved release PR publishes both changes.

Open questions

Whether run_script should also accept the timed deliveries of a real scope, so one script drives both unit and acceptance tests. This can be decided in group 1 without a change to the specs.
